## 1. 决策摘要

建议升级为“本地恢复控制器＋受限远程运维能力＋可恢复安装事务”的 Windows agent。技术上可行，现有后台可以复用身份验签、策略版本、发布目录和管理控制台；现有客户端可以复用下载校验、服务入口和部分安装能力。

决定成功与否的工作不是增加多少命令，而是以下六项：

1. 将安装完整性、Windows 服务、应用就绪、远控注册、API 连通分别判断。
2. 明确主动停用、本地禁止恢复、远程暂停、安装维护四种不同语义。
3. 主程序更新、agent 自愈、远程安装使用同一机器级互斥和安装事务协议。
4. agent 停止前，独立 helper 和重启接续机制已经就位。
5. 命令支持持久化去重、断点恢复、结果补报，不能仅承诺“执行一次”。
6. 在旧版 EXE/MSI 的真实在线更新中证明运行中的 agent 被成功替换。

推荐分阶段交付，最终包含完整事务能力。首阶段只上线观测与低风险服务恢复，第二阶段开放完整安装恢复，第三阶段开放远程运维和 agent 自更新。任何阶段都不能把尚未完成的能力显示为已支持。

用户补充的最终验收要求：主程序意外下线后，agent 必须主动救活并具备多种 fallback；现有可在线更新的主程序和旧 agent 应通过一次兼容升级，获得新 agent 全部适用能力。最终交付包含第 7.4–7.6 节的恢复阶梯和离线资产、第 12.7 节的 agent 独立保底入口、第 15.5–15.8 节的首次迁移以及第 17.6 节的组合故障验收。仅状态上报、远程按钮、单次服务重启或主程序版本更新，不满足最终交付要求。

## 2. 范围、目标与能力边界

### 2.1 用户目标

- 异地 Windows 设备无需登录桌面，即可恢复意外停止的主服务。
- 服务缺失或配置损坏时可以修复；没有可信可用客户端时可以恢复安装。
- 主程序离线时，后台仍能独立观察 agent，并下发已实现的恢复动作。
- 更新失败、断网、重启和重复命令不得导致恢复风暴或静默丢失管理能力。
- 已有设备 ID、UUID 绑定、密钥、业务配置和版本信息有明确保留规则。
- 后续后台可以组合和调度已有能力；新增本地能力通过 agent 升级引入。
- 主程序停止、挂起、文件损坏和更新失败时，自动逐级选择恢复路径，不依赖后台实时在线才能开始。
- agent 自身崩溃、意外停止或升级中断时，有独立于 agent 主进程的保底启动入口。
- 健康期间持续维护离线救援资产；不能等故障后才第一次准备保底包和凭据。

### 2.2 明确边界

- 首版面向 Windows standard/SOS、x86_64 EXE/MSI 四种组合。
- Linux、macOS、Android 不增加 management agent；现有更新协议继续兼容。
- Android 始终只发布 standard APK；不产生 Android SOS 目标。
- 不提供任意 cmd、PowerShell、任意服务管理、任意路径操作或任意程序运行。
- 操作系统不启动、磁盘物理故障、所有恢复文件和服务被管理员完整删除、网络被整体封禁，不属于 agent 能独立解决的故障。
- agent 与主程序运行在同一台机器，且通常共用网络、系统和凭据来源，不能宣称具有完整故障隔离。
- 本文中的接口、表名、状态字段和阈值是建议契约，不代表现有实现。

### 2.3 固定约束

保留仓库约定的服务器、API、公钥、密码、认证方式和默认权限。客户端继续使用 `https://download.yan.life` 下载，Actions 上传继续走 OSS 加速域名。构建产物仍由手动 Flutter Tag Build 产生；GitHub Release 标题仅为 tag，正文和 tag 说明为空。不得借此次 Windows 改造调整 macOS 签名链或 Android 长期证书。

后台只扩展当前有效的 SQLite 实现，MySQL 保持冻结。管理接口使用 `${RUSTDESK_ADMIN_PATH}`，不得引入公开固定 `/admin` 入口。

### 3.1 对原始故障描述的修正

原始文档将 YXJ 的 401 归因于反代路径。当前两端源码中的 canonical path 一致，不能凭这些代码确认该根因。应将其标记为“历史诊断，待生产版本与请求证据复核”。

需要区分：缺少签名头、时间偏差、公钥未登记、公钥变化、身份解析变化、正文摘要不符、签名路径不符，以及代理改写或过滤。不能把所有 401 合并成路径问题。

YJ 没有 `policy/stream` 请求，只能证明该管理链路未被观察到；不能单凭它确认 Windows 服务停止。需要 SCM 状态、进程路径、主程序日志和设备心跳相互印证。

### 3.2 DTF 双服务停止的独立恢复要求

原始需求新增 DTF（ID `512655010`）：主程序与 agent 的最后请求均为 200，用户恢复被隔离文件、加入信任区并退出托盘后，两条请求链都消失。本文不据此确认服务一定被停止；实施前仍需 SCM、启动类型、实际文件/拦截和事件日志证据。

该场景必须独立覆盖：agent 正常停止不同于崩溃，SCM failure action 不保证拉起；文件恢复/信任处理也不等于服务 Running。依靠计划任务 bootstrap 先检查批准 agent 文件和服务契约并启动，再由 agent 按本地意图恢复主服务。

DTF 第一层验证“两个服务注册仍在、文件已恢复、启动类型未禁用”：无人工 sc start、无后台命令，周期/开机入口救活 agent，主程序随后恢复。另测文件仍隔离、服务 Disabled、计划任务缺失、再次启动被拒绝和主动停用；这些情形必须报告实际限制和退避，不关闭安全软件、不自动添加排除项。

若两个程序及 bootstrap/任务都被安全软件统一阻止或删除，本机恢复链无法保证执行，应走已有授权带外管理或现场处置。不能以多入口存在宣称抵抗所有同机共因故障。原始文档的“这次不改代码”描述现场临时处置，后续 agent 升级要覆盖其对应故障。

## 4. 架构选择与可行性

### 4.1 方案比较

| 方案 | 优点 | 局限 | 结论 |
| --- | --- | --- | --- |
| 仅增加服务启动检查 | 改动小，快速缓解服务停止 | 无法处理更新冲突、自更新、断电和远程诊断 | 作为第一阶段能力 |
| agent 本地控制器＋独立命令＋事务 helper | 可复用现有基础，责任清楚，可逐步迁移 | 必须设计持久化和安装接续 | 推荐最终架构 |
| 所有功能放入主程序 | 接口少 | 主程序丢失时恢复能力一起丢失 | 不满足目标 |
| 通用远程 shell | 临时操作灵活 | 无法给出受限副作用和明确验收；扩大 LocalSystem 权限暴露 | 不采用 |
| 永久第三个完整运维服务 | 可覆盖更多进程退出 | 形成两套恢复决策和升级竞争 | 不采用 |
| 计划任务＋小型固定启动器 | 主 agent 不运行时仍有恢复入口 | 同机共因故障仍存在，需防重复执行 | 纳入最终方案，只救 agent 和接续事务 |

### 4.2 推荐的职责划分

| 组件 | 职责 | 不承担的职责 |
| --- | --- | --- |
| RustDesk 主程序 | 远控、业务就绪探测、当前身份和运行意图发布、正常更新入口 | agent 不存在时的自恢复 |
| Management Agent | 状态采集、最小恢复决策、命令校验、任务调度、结果补报 | 在自身服务回调中同步等待长安装 |
| 恢复 helper | 执行一笔受验证事务、恢复服务、写结果 | 接收后台通用命令 |
| 临时恢复任务 | helper/agent 中断或重启后接续当前事务 | 周期性无限重装、重新获取任意任务 |
| 常驻保底启动器 | 开机和周期核对 agent，必要时恢复批准的本地版本 | 第二套主程序自愈、远程命令、任意下载执行 |
| PHP API＋SQLite | 身份授权、策略、命令持久化、状态投影、管理 API | 保持每台设备的长连接 |
| Go broker | 后续可选实时唤醒和通知 | 执行命令、代替数据库命令事实 |
| 管理页面 | 展示来源明确的状态、创建命令、查看真实结果 | 将 HTTP 200 或“已发送”显示为修复成功 |

```text
管理页面 → 管理 API → SQLite 策略 / agent 命令
                             ↑           ↓
                      签名状态与事件   签名短轮询
                             ↑           ↓
                       Management Agent
                       │             │
                 SCM / 本地 IPC   安装事务＋互斥
                       │             ↓
                  RustDesk     独立 helper ← 临时恢复任务
                                     │
                              验证包 / 应用 / 恢复
```

首版采用短轮询。保留现有 `/agent/policy`；新增状态、命令和包解析接口。将来增加 SSE 时，复用 Go broker 的基础设施，增加 agent 专用路由和容量配额。短轮询始终是可用的回退通道。

## 5. 状态模型与判断依据

### 5.1 状态分为三个层次

- `desired`：管理员策略和明确本地意图。
- `observed`：SCM、进程、本地 IPC、文件和网络的当前观测。
- `operation`：正在执行的动作、事务阶段、下次允许动作时间。

健康状态不能反向修改管理员策略。客户端上报“当前未恢复”不等于管理员希望关闭恢复。

### 5.2 必须独立记录的维度

| 维度 | 建议取值 | 可靠性规则 |
| --- | --- | --- |
| 安装 | `valid/missing/corrupt/unverified/unknown` | 文件存在只能支持 exists，不能直接支持 valid |
| SCM 服务 | `absent/stopped/start_pending/running/stop_pending/paused/unknown` | 查询失败不等于不存在 |
| 本地应用 | `ready/unresponsive/starting/unknown` | 区分服务宿主与真正业务进程 |
| 远控注册 | `registered/disconnected/unknown` | 来源为主程序报告；没有 hbbs 集成时不是服务端独立验证 |
| 主程序 API 心跳 | 现有 `online/recent/offline/unreported` | 继续使用原有心跳阈值 |
| agent 联络 | `online/stale/offline/unreported` | 使用 agent 自身认证上报时间 |
| 运行意图 | `enabled/disabled/unknown` | 包含来源、revision、最近可靠读取时间 |
| 恢复权限 | `enabled/remote_paused/local_blocked` | 本地禁止最高优先级 |
| 维护 | `idle/in_progress/reconciling/blocked` | 以有效事务证据为准 |

每项观测带 `observed_at`、`source` 和有效期。过去的 ready 不能无限沿用。页面允许显示“未知”，禁止把缺失字段自动显示为正常或异常。

### 5.3 本地应用就绪探测

建议增加只读、低成本的本机 IPC。Windows 服务模式存在宿主和业务进程层次，实施前核对实际进程树，将探测落到能回答关键业务状态的进程。

响应包含：协议版本、PID、启动实例号、程序版本/build_seq、实际可执行路径、运行意图、配置加载状态、远控注册状态、活动会话数量、安装事务号。

- 单次超时建议 2 秒；连续 3 次失败且持续至少 60 秒，才判为持续无响应。
- 管道只允许 SYSTEM 和授权服务主体访问；验证客户端/服务端身份，避免普通用户伪造 ready。
- 响应绑定启动实例，使用单调时间计算活性；不能使用一个长期存在的健康文件。
- IPC 无法证明画面、输入和提权全部可用，实际远控连接仍需 E2E 验收。
- 旧主程序没有 IPC 时上报 `unknown/legacy`，保留 SCM 启动能力，不据此自动判定卡死并重装。

### 5.4 发布能力与当前可用能力

实施时维护版本化 `capabilities.json`，绑定构建身份和测试编号，并由实际 dispatch/构建 feature 核对。不能仅依据主程序版本号推导 agent 命令存在。每项分别记录 `supported`、`enabled`、`ready` 和 `blocked_reason`；权限关闭、维护中、缺缓存不会使 supported 消失。

发布能力范围至少包含测试手册第 2.3 节；结合当前源码、UI 和发布契约补齐所有已支持主程序功能。遗漏已有功能是测试缺口，不能通过删能力条目变成全量通过。构建清单用于支持判断，进程响应和真实 E2E 证明实际可用。

## 6. 用户意图与策略优先级

### 6.1 优先级

由高到低：

1. 本地管理员明确设置的禁止恢复或彻底卸载标记。
2. 已经开始的事务的安全收尾：完成不可分割阶段或恢复旧可用状态。
3. 有效维护事务对新动作的互斥。
4. 明确的客户端主动停用意图。
5. 后台恢复策略及已批准的一次性命令。
6. 本地自动恢复规则。

禁止恢复出现后，不启动新安装；已进入替换阶段的事务必须安全收尾，不能在文件切换中途退出。远程命令不能删除本地禁止标记。

### 6.2 三种“关闭”不能混用

| 操作 | 语义 | agent 后续行为 |
| --- | --- | --- |
| 关闭恢复策略 | 暂停恢复动作 | 继续上报、轮询、接受重新启用策略 |
| 停止客户端服务 | 用户希望远控服务不运行 | 保留意图，不自动拉起 |
| 禁止恢复 / 彻底卸载 | 本地管理员禁止自动恢复 | 不允许远程覆盖；彻底卸载清除受管组件 |

保留 `disable-recovery` 作为本地禁止标记；远程暂停不能使用该文件。单纯禁止恢复且 agent 尚在时，可继续只读上报；彻底卸载按明确卸载流程处理。

### 6.3 `stop-service` 的读取和迁移

agent 使用显式失败的读取函数区分不存在、权限拒绝、解析失败和有效 `Y`，不直接借用会吞掉错误的 getter 判断意图。

运行中的主程序通过 IPC 发布当前有效意图；服务停止时，读取受保护的意图记录及服务配置来源。正常停用路径需在停止/删除主服务之前持久化意图，安装维护停止则写入维护事务，不冒充主动停用。

旧客户端意图缺失时，进入 `intent_unknown` 并上报；不清空配置、不恢复出厂、不自动执行重装。已由可信安装流程记录为运行、且没有更新的停用证据时，才使用最后可靠意图。首次升级必须建立该记录，避免所有旧设备永久卡在 unknown。

首版 `service.start/restart/reconcile` 不覆盖明确主动停用。确需远程重新开启客户端，另设 `client.enable@1`：要求显式管理员确认、当前意图 revision 和客户端能力支持；不能覆盖本地禁止恢复。`recovery.enable` 仅表示允许恢复，不能暗中等价于启用远控。

### 6.4 服务端期望与实际应用分离

既有 `management_agent_enabled` 继续表达管理员期望。新状态独立记录 `effective_recovery_enabled`、`applied_policy_revision`、`blocked_reason`。

现有 runtime 同步可回写该字段，见证据第 3 节。新增 agent 状态接口不得调用此同步函数。实施时只对 agent 专属字段明确管理员单向权威，保留其他更新选项既有行为，并增加旧上报兼容测试。

## 7. 本地恢复状态机

### 7.1 一轮检查顺序

1. 检查系统关机、服务停止请求和本地禁止。
2. 恢复或核对未完成事务，禁止同时创建新事务。
3. 采集意图、SCM、文件和应用状态。
4. 无论健康与否都按独立调度进行上报、策略刷新和命令接收。
5. 合并当前策略、命令和本地恢复需求，选择唯一改变系统状态的动作。
6. 取得机器级互斥后重新采样前置条件；条件变化则推迟。
7. 持久化操作意图，执行动作，验证后置条件，再持久化结果。
8. 更新退避和动作预算；网络补报不触发动作重做。

网络请求不得阻塞本地检查和 SCM stop 回调。使用有界工作队列和超时；不为每一轮无限创建线程或任务。

### 7.2 决策表

| 条件 | 动作 | 升级或退出条件 |
| --- | --- | --- |
| 查询服务被拒绝或失败 | 上报错误 | 不解释为服务缺失 |
| 明确停用、本地禁止、意图未知 | 不改变运行与安装状态 | 继续观测，等待可靠意图或允许的显式命令 |
| 有效安装事务进行中 | 延迟其他变更 | 仅核对进度；疑似中断进入事务恢复 |
| Start/Stop Pending | 按 checkpoint、wait hint 等待 | 达到有界总超时后采集证据并限制恢复 |
| 服务 stopped，可信安装完整 | 启动服务 | Running＋本地 ready；旧版以较弱验证单独标注 |
| 服务不存在，可信安装完整 | 注册标准服务配置 | 保留配置和身份，验证启动 |
| binpath、启动类型等配置异常 | 修正必要配置 | 优先 ChangeServiceConfig，不默认删除重建 |
| 主安装无效，可信保底安装兼容 | 切换保底服务路径 | 标记 degraded，不每轮来回切换 |
| 无可信安装，运行意图明确允许 | 使用批准恢复包执行安装 | 包验证、事务和本地就绪验证 |
| Running＋本地持续无响应 | 收集诊断后一次受控重启 | 有活动会话或状态未知时默认推迟破坏性动作 |
| 本地 ready，仅 API/ID 服务异常 | 网络诊断、退避、告警 | 不自动重装 |
| 同目标版本反复启动失败 | 暂停该目标的自动安装 | 保留可用旧版本，等待明确批准目标 |

文件存在但损坏、无法运行或依赖缺失纳入恢复条件。服务已标记删除、句柄尚未释放等情况按 Windows 错误处理，不能固定睡眠后假设删除完成。

上表“Running＋本地 ready”是目标判据；当前 R1/R2 的成功确认只到 SCM `Running`（`windows.rs` `start_existing` 注释即写明“确认 SCM 状态转换，不宣称远端/应用就绪”），R3 例外，会额外做一次健康探测。后果是服务进程起来但注册/ID 未就绪时，R1 记成功并清空 `service_recovery_error`，不会再升级到 R3。而“文件存在但损坏”这条恢复条件尚未实现：R3/R4 只识别缺失，不比对内容，详见 7.4 节后的差距说明。

### 7.3 建议初始阈值

以下为试点参数，必须用实际包测量后确认；服务端只可在客户端限定范围内调整。

| 项目 | 建议值 | 说明 |
| --- | --- | --- |
| 本地检查 | 30 秒 | 不被网络请求延后 |
| 启动/唤醒宽限 | 180 秒 | 继续观测与上报，限制自动干预 |
| 本地启动就绪上限 | 90 秒 | 结合 Pending 进度，可在限定上限内延长 |
| 轻量服务恢复退避 | 30 秒、120 秒、300 秒 | 15 分钟最多 3 次自动重启 |
| 安装失败退避 | 5、15、30、60 分钟 | 24 小时最多 3 次自动安装尝试 |
| 同目标熔断 | 达到自动安装预算 | 不能每次联网或重启就清零 |
| 健康稳定复位 | 连续 ready 10 分钟 | 单次短暂 Running 不清空失败预算 |
| 状态上报 | 60 秒，变更立即合并上报 | 抖动 ±20%，事件限流 |
| 命令短轮询 | 30 秒 | 抖动 ±20%，空响应不创建历史事件 |

API 401、403、429、5xx、DNS/TLS 故障使用网络专属退避，与本地启动预算分离。尊重 `Retry-After` 并设上限；401 不降级为匿名命令获取。

系统重启和时钟回拨不能重置动作预算。进程内超时使用单调时钟；跨重启日历时间异常时采取保守限速并上报，不能因时间错误跳过包验签或命令有效期检查。

当前实现与本表对账：轻量服务恢复退避（30/120/300 秒，封顶后固定 3600 秒）、安装失败退避（5/15/30/60 分钟）已落地；健康稳定复位的判据是连续 `Running` 且 binpath 可信满 10 分钟，不是“连续 ready”。未落地的三项是“同目标熔断”（没有熔断态，封顶后无限重试）、“24 小时最多 3 次自动安装尝试”（没有次数上限）和“跨重启不重置预算”（只对 R1–R3 成立，自动 R4 worker 的预算在内存里，agent 重启即清零）。后果是后台看不到“已熔断”或“冷却至何时”，只能看到一个 `service_recovery_error` 字符串。补齐需要新增状态与生命周期规则，须维护者批准。

### 7.4 主程序救活阶梯与 fallback

按故障类别选择恢复层级，每次动作重新检查前置条件、保存真实结果；成功后停止升级动作。网络或远端故障不进入文件重装链。

| 层级 | 适用情况 | 恢复办法 | 后续 fallback |
| --- | --- | --- | --- |
| R0 | 本地业务进程存活，注册连接疑似卡住 | 固定 IPC 请求注册重连 | 本地故障证据成立后进入 R1 |
| R1 | 服务停止或业务进程确认无响应 | 启动或一次受控重启 | 读取退出码与配置，判断 R2/R3 |
| R2 | 服务缺失、启动类型/参数/binpath 错误 | 修正服务配置，缺失时重建 | 配置正确但现有版本无法启动则 R3 |
| R3 | 主安装不可用，有可信兼容保底客户端 | 切换完整保底客户端的服务路径 | 保底不可用则 R4 |
| R4 | 现有安装均不可用，有批准离线包 | 本地包重新提取或修复安装 | 本地包损坏/不适用/失败则评估 R5 |
| R5 | 需要重新取得包且网络可用 | API 精确解析；失败时使用预先批准的签名目标引用下载修复 | 同目标熔断；只允许另一个批准且兼容的目标 |
| R6 | 允许路径均失败或被限制 | 保持 agent 管理、轻量观测、告警和条件重评估 | 不无限重装，不擅自重启整机或清空身份 |

上表是目标阶梯。按 2026-10-23 只读核实，当前代码与它的差距只在下述范围，测试判据以差距说明为准：

- R3/R4 与 agent 备份恢复只接受 MSI（`windows-x86_64-msi-*`），EXE 两包没有这些路径；四包矩阵里 EXE 的 R3/R4 用例应记 `NOT_APPLICABLE`。
- R3 只识别主安装目录或 `RustDesk.exe` 缺失，不识别“文件在但内容被替换”；自动 R4 更进一步，只在整个 `C:\Program Files\RustDesk` 目录缺失时才触发。后果是主程序被换成长度/哈希不同的同名文件时，R1 会反复 `StartService`（30/120/300/3600 秒退避），R3 不切保底、R4 不触发，设备停在启动失败循环且没有降级路径；被替换的程序若能运行还会被当作可信服务拉起。两者口径不同，用例需分别构造。
- R5 自动路径只取 manifest 的 `target.primary`，不读镜像；主 URL 404 后按 5/15/30/60 分钟退避重试同一 primary。而设备上存在 `rescue\current` 签名 bundle 时（MSI 首装后即存在），自动 R5 整体被跳过，只剩远程命令下载。镜像回退只在远程命令路径（`package_download::download`）生效。另外 R5 失败写的是 `agent.json` 的 `last_error`/`retry_stage`/`next_check_at`，这三项都不在状态上报 payload 里，后台看不到 404 原因，只能查本地文件或日志。
- R6 没有熔断态、冷却期和告警事件：只有一个退避预算，30/120/300 秒后固定 3600 秒，无次数上限；自动 R4 worker 的预算只在内存，agent 重启即清零（同目标重做仍被 attempt 目录占用阻止）。后果是后台只能看到 `service_recovery_error` 文本和 rescue 快照，看不到“已熔断/冷却至何时/需要人工”。
- 停滞看门狗与 Task Scheduler degraded 上报均未实现；`rescue.components.recovery_entry` 恒为 `not_assessed`。后果是主循环卡死后 R1–R5、上报和命令领取全部停摆，SCM 与 bootstrap 都看到 `Running` 而不动作，直到人工重启。

以上差距中，“自动 R5 接入镜像回退”可复用现成函数、不新增状态；其余（R4→R5 阶梯跃迁、熔断状态、跨重启预算、篡改识别、EXE 恢复资产、停滞进度戳）都需要新增状态或新生命周期规则，按 AGENTS.md「Corner cases raised in review」须维护者批准后才实施。

R0 是新增能力，通过 Windows 主程序薄 IPC 钩子复用已有注册重连路径，不修改固定服务器、公钥或认证。IPC 不可用时直接按可靠观测选择 R1/R2，不等它恢复。

R3 必须恢复完整客户端及服务运行模式，不能以 SYSTEM 启动一个桌面 GUI 进程充当远控服务。成功后标记 degraded，正常安装修复作为后续独立事务。

R4 无需公网，R5 无需主程序运行。API 不可用时，R5 只使用已有批准策略允许的签名目录或目标引用，不无条件安装动态 latest。

恢复目标顺序：当前构建修复 → 最后验证可用且配置兼容的版本 → 明确批准的新修复版本。退回最后可用版本属于明确本地恢复契约，与远程 package.update 禁止任意降级不同；不可逆配置迁移或已撤销包禁止回退。

熔断的是同包/版本/错误类别，不是永久停止全部 fallback。继续升级须有新条件，例如另一份正确缓存、兼容保底版本、网络恢复后的正确下载；不能更换命令号重复失败动作。所有安装和运行状态切换仍受总预算约束。

候选包先在 staging 下载验证，不持安装锁等待网络。进入维护和切换前取得互斥并重新核对前置条件。已有未完成事务时优先接续/恢复，不另开“重装 fallback”。

### 7.5 服务 Running 但长期离线

SCM Running 不能结束检查；“会话未知”也不能让挂起程序无限 deferred。建议规则：

1. 同时观察本地 ready、注册状态、主心跳和 agent 固定目标探测。
2. 仅主心跳或 policy/stream 缺失归类为上报异常，不能证明远控不可用。
3. 本地 ready 但注册持续失败、固定目标可达时，至少观察 5 分钟并排除维护/主动停用，先尝试 R0。
4. 重连后仍失败且可靠确认无活动会话，允许一次 R1；重启后继续观察，不直接重装。
5. agent 的 HTTPS 探测成功不能证明主程序 UDP/TCP 注册链路均正常，仅作诊断证据。
6. IPC 连续无响应、业务进程无进度持续 10 分钟且会话无法确认时，可按预先启用的 `unresponsive_restart_allowed` 救援策略执行一次有界重启，记录潜在会话中断。
7. 单纯网络失败或心跳缺失不满足第 6 项。重装和整机重启不因会话未知自动放行。

第 6 项明确取舍可用性与潜在会话中断：异地部署可启用一次无响应救援，保守部署可关闭。页面显示实际策略和延迟原因，不能隐藏无限推迟。重启后仍离线但本地 ready 时保留诊断，等待链路恢复或明确命令。

### 7.6 健康期间的救援准备

安装成功及每次稳定更新后，准备完整保底客户端、批准离线包、签名元数据、身份配置备份、agent 备份和启动器。至少每 24 小时及资产变更后检查；大文件 hash 在低优先级有界任务执行，不每轮全量扫描。

恢复资产损坏时，趁主程序健康重新准备，不因此重启主程序。空间不足先清理可删除 staging/日志，不先删除唯一恢复包、未完成事务备份或原身份。

新增 `rescue_readiness=ready/degraded/unavailable/unknown`，分别展示服务恢复、保底客户端、离线包、在线包源、启动器、凭据可用性和验证时间。agent 在线不等于救援准备齐全。

异地“完整保护”要求离线包、保底客户端、原身份恢复和 agent 启动器全部通过验证；缺少一项阻断依赖它的高风险动作，其他可用能力继续保留并告警。

## 8. 设备身份、认证和登记迁移

### 8.1 复用的基础

复用现有设备签名头、Ed25519、设备公钥登记和 nonce 防重放。设备 ID＋UUID 继续对应管理对象；增加 `agent_installation_id` 标识本次 agent 安装实例，增加 `enrollment_generation` 表达后台绑定代次。

新 agent 接口使用精确身份，不使用 `RustDesk Yan` 模糊别名解析。保留旧接口兼容路径，不把旧接口解释规则复制到新命令执行链。

### 8.2 首次登记与离线恢复

当前“最近 90 秒上报后首次绑定公钥”属于有限条件的首次使用信任，近期上报本身不是独立的设备所有权证明。它不能被直接升级为 LocalSystem 恢复命令的完整信任基础。

推荐登记流程：

1. 安装或在线迁移时取得已有设备公钥、精确身份和 agent 安装实例。
2. 对已有可信部署记录或已登记密钥进行一致性核对；不是无条件信任任意已有键。
3. 管理员为该实例激活 agent 运维权限，或使用受控部署签发的一次性登记授权绑定公钥指纹、设备身份和用途。
4. 具备可信既有密钥的设备可由策略做批量激活，但需要保留来源与迁移审计。
5. 没有可信记录且主程序已经离线的设备，等待已有授权通道或现场部署完成登记；不得仅延长 90 秒窗口解决。

普通旧更新接口继续兼容；高权限 agent 命令要求 `agent_authorized` 绑定。主程序当前心跳不再是已授权 agent 日常访问的必要条件。

### 8.3 本地凭据保留

- 保留现有身份数据，在受保护目录保存恢复所需的绑定元数据和凭据备份。
- 私钥备份必须经机器保护并限制 ACL，不能明文进入日志、命令参数或诊断包。
- 机器范围保护不能替代 ACL；同机管理员/SYSTEM 不属于可隔离攻击者。
- 无法读取原身份时进入 `identity_unavailable`，禁止调用会生成新 ID/密钥的路径冒充恢复。
- 主程序和 agent 共享原设备私钥意味着二者认证权限不能仅凭一个 `component` 字段隔离。后台记录组件用于路由和审计，不把它当作密码学隔离。
- 独立 agent 密钥可作为后续版本能力，必须经过已有信任的登记、轮换、撤销和迁移；首版不同时引入新的 PKI。
- ID 变化、UUID 变化、重装操作系统和克隆机器均产生身份重核流程，禁止自动按主机名合并。

### 8.4 签名契约

保留 auth-v1 canonical payload 和既有接口路径。新 POST 接口签名包含请求正文摘要、精确设备身份和命令号；影响授权的参数放入正文，不依赖未签名查询参数。

`GET /agent/commands` 的设备选择只使用签名身份，返回目标也必须精确匹配；游标和 limit 只用于分页，不得改变操作授权、目标包或执行参数。未来若需要把完整查询纳入签名，单独发布 auth-v2，不能静默修改 v1。

两端固定测试向量覆盖直接 URL、`index.php?s=` 路由、Nginx rewrite、尾斜杠和错误路径。实际验签路径使用约定的外部逻辑路径，不信任来自公网的任意 forwarded path 头。

### 8.5 认证失败可观测性

响应提供稳定 `error_code`、`request_id` 和必要的 `server_time`，例如 `missing_credentials`、`clock_skew`、`key_not_registered`、`key_mismatch`、`signature_invalid`、`nonce_replayed`。

后台按原因聚合和限流记录；不记录私钥、完整签名或凭据。验签失败请求中自报 ID/UUID 只能标为“未验证身份提示”，不能据此更新该设备可信 agent 在线状态。

本地自愈在 API 不可达或认证失败时仍可按最后有效策略运行；不能将请求失败解释为重新启用恢复。客户端时间错误只报告，不由 agent 擅自修改系统时间。

### 8.6 实例与版本变化规则

普通 agent 版本升级保留 installation_id 和绑定代次，能力/版本按新进程重新确认；不能每次替换 exe 都创建新身份、使已领取命令失效。彻底重新登记、身份重置或撤销后重新授权才显式更新 generation，并先对账旧事务/命令。

boot_id 不是可排序时间戳。服务端以认证的启动会话记录当前 boot，只有当前会话的递增 sequence 可更新投影；迟到的旧 boot/旧实例不能靠“不同 boot_id”覆盖新状态。状态/事件分开接收：旧运行阶段的合法动作终态仍可留历史，但不更新当前在线/健康投影。对应乱序/重启测试必须实现，不能只比较数字 sequence。

## 9. API 契约

### 9.1 设备接口

| 方法与路径 | 用途 | 核心约束 |
| --- | --- | --- |
| `GET /rd/update/v1/agent/policy` | 保留旧策略 | 旧字段保持，扩展字段有版本说明 |
| `POST /rd/update/v1/agent/enroll` | 完成受控登记 | 一次性授权或已批准绑定＋设备签名 |
| `POST /rd/update/v1/agent/status` | 最新状态与能力 | 始终签名；不更新主程序 last_heartbeat |
| `GET /rd/update/v1/agent/commands` | 有界获取可投递命令 | 已授权设备；不在 GET 中领取执行权 |
| `POST /rd/update/v1/agent/commands/{id}/claim` | 领取指定命令 | 签名正文、安装实例、绑定代次、命令号 |
| `POST /rd/update/v1/agent/events` | 动作和事务事件 | 始终签名，包括无远程命令的本地自愈事件 |
| `POST /rd/update/v1/agent/package/resolve` | 精确解析批准恢复包 | 验证 edition、架构、包类型、命令与策略 |

包解析应复用现有 release 选择纯逻辑，不要求已有安装必须有可比较版本；同版本修复允许返回安装载荷。不能直接套用“当前已是最新版本则无下载载荷”的主程序更新检查行为。

当前本地恢复事件的枚举只有 R1/R3/R4（`local_events.rs` `RecoveryCode`），动作只有 `StartService/RestoreFallback/RepairInstallation`。R2 修复 binpath、R0 重连注册、自动 R5 下载安装、bootstrap 拉起/恢复 agent 都不发事件，只写 `agent.json` 或日志；R6 无独立状态。R2 有 `last_service_recovery_at` 状态投影，但投影不等于事件。扩展事件枚举属于协议与持久化格式变化（outbox 记录、后台枚举、旧后台兼容），每类事件还要引入新的 operation 生命周期，且需后台仓库 rd-api 配合，须维护者批准。

所有响应 `Cache-Control: no-store`；命令响应限制为最多 20 项和 256 KiB。空队列返回 200＋空数组。分页必须能前进，不能让一个 unsupported 或长期运行的命令永久挡住后续诊断命令。

### 10.1 建议首批命令

| `package.verify@1` | 校验安装及缓存完整性 | 固定受管目录 |
| `package.reinstall@1` | 同版本或指定批准版本修复 | 精确包目标，事务、磁盘与权限检查 |

| `client.enable@1` | 显式改变主动停用意图并尝试启动 | 单独能力、意图 revision、管理员确认；不覆盖本地禁止 |

`file.exists` 改为逻辑对象完整性查询，不接收任意路径。`recovery.enable/disable` 优先通过策略维护长期期望；若保留命令别名，必须映射为带期望 revision 的策略变更，不能形成第二份独立开关。

### 10.3 生命周期

```text
pending → accepted → running → succeeded / failed / rolled_back / rollback_failed
   │         │          └── reconciliation_required
   │         └── deferred → running
   └── expired / cancelled / unsupported / rejected
```

- GET 可重复投递；claim 在事务中由 pending 转 accepted，并绑定安装实例和代次。
- 同一实例重复 claim 返回原领取结果；其他实例不能接管。
- accepted 在设备本地代表命令已可靠写入日志，不代表动作已开始。
- 自愈和远程命令进入同一执行器；每台设备同时最多一个改变系统状态的动作。
- pending 到期禁止新领取；已领取但尚未开始，到期后报告 expired。已开始的安装不因命令到期中途退出。
- deferred 在原命令有效期内重评估；开始前重新检查意图、会话和包目标。
- 未收到进度时后台显示执行未知或联络中断，不能仅凭超时宣称失败、成功或重新派发。
- agent/机器崩溃后，按本地日志与事务恢复，不能盲目重新执行 restart。
- cancelled 只保证尚未开始的任务不执行；无法撤回已产生的副作用。
- 执行前与关键变更前复核本地禁止、维护状态和命令前置条件。
- 同一命令 ID 不同正文摘要必须拒绝；重复合法事件不产生重复动作。

### 10.4 持久化与补报

本地保存命令 ID、正文摘要、claim 结果、动作开始记录、事务号和最终结果。结果持久化成功后进入 outbox，使用稳定 event_id 重试上报；每次 HTTP 重试重新生成 nonce 和签名。

后台已接受但本地尚未落盘时崩溃，同一实例可重新取得领取记录；本地落盘但 ack 丢失时可幂等重试 claim。日志损坏时禁止非幂等自动重做，进入 reconciliation_required。

命令有效期最长建议 24 小时；终态去重记录保留 30 天，同时拒绝过期新执行。未确认结果和未完成事务不得因保留期到期删除。持久化不可用时拒绝新的状态变更动作，允许诊断。

设备重新安装 agent 后，旧实例未完成命令不自动转给新实例；先核对实际状态，记录对账结果，再由管理员创建新命令。

### 10.5 与旧主程序更新的协调

新 agent 命令进入独立队列。旧 check/install 继续由主程序消费，不把新命令放入旧 SSE。

两种入口在客户端汇合到安装互斥与事务协议。后台发现活跃 agent 安装事务时暂停创建冲突 install；客户端互斥仍是最终裁决，不能只靠后台状态缓存。旧主程序不支持协调时，仅开放观测或明确维护窗口中的低风险恢复，禁止以“没有收到维护状态”推断没有更新。

### 10.6 持久化领取、离线队列与资源上限

claim 的数据库状态与本地可靠接收分开：agent 先保存命令摘要和领取意图，再请求 claim；后台 accepted 只表示绑定实例已领取。agent 将返回结果可靠保存后报告 `receipt_persisted`，才允许执行。本地落盘失败不执行，断线后仍可查询/幂等领取该实例的命令，不仅重新 GET pending。

明确事件 ack 包含已接收 event_id；HTTP 超时不能推断后台未写入。同 event_id 内容不变可补报，不同内容返回 conflict，最终状态与动作事实不因回报丢失重新执行。

建议固定初始上限，纳入压力与磁盘故障测试：

| 资产 | 初始上限/处理 |
| --- | --- |
| 命令等待队列 | 每设备 100 个未终态命令；创建超限返回 429 并提供重试提示 |
| 单次命令/事件 | 单命令参数 ≤16 KiB；单事件 ≤64 KiB，diagnostics 另走限量包 |
| outbox | 10,000 项或 64 MiB；可合并未发送普通状态，不能删除动作终态/事务事实 |
| 普通日志 | 总 100 MiB 轮转；失败事务与必要去重记录不当作普通日志轮转 |
| 恢复磁盘需求 | 包＋提取目录＋旧目录备份＋事务空间＋至少 512 MiB 余量，按实际包测量 |

outbox 满时保留结果、上报 backlog，暂停需要新增可靠事务记录的安装，允许仍能安全留证的轻量恢复/诊断；状态文件不能写时停止新变更。不得为了“让任务继续”删除未确认终态、原身份或唯一救援资产。

安装互斥是跨进程最终边界，维护记录是崩溃接续证据，不是另一把仅按时间过期的锁。持有者采用 PID＋创建时间/实例和 transaction_id 核对，避免 PID 复用；时间超限先核对 SCM、helper、MSI 实际活动，不自动抢占活着的安装。

## 11. SQLite 数据设计与后台职责

### 11.1 建议增量表

| 表 | 关键字段 / 索引 | 作用 |
| --- | --- | --- |
| `device_agent_bindings` | PK(device_id,uuid)，installation_id，generation，key_fingerprint，authorized，revoked_at | agent 运维授权和实例归属 |
| `device_agent_status` | PK(device_id,uuid)，installation_id，boot_id，sequence，server_received_at，payload | 最新可信状态，不无限追加心跳 |
| `device_agent_commands` | PK(command_id)，设备、实例、type/version、args、digest、状态、有效期、操作者、idempotency_key | agent 专属命令事实 |
| `device_agent_events` | PK(event_id)，命令号、operation_id、attempt、sequence、stage、result、payload、服务端时间 | 自愈、命令、事务历史 |
| `agent_operations_audit` | actor_id、设备、动作、参数摘要、授权结果、reason、request_id、batch_id | 精确运维审计 |

包目标首先复用现有 `update_releases`，增加不可变目标引用或等价映射，不复制一份动态 latest。当前发布校验检查签名字段形状和 key id，不等于已完成密码学验签；包执行前 agent 仍必须独立验证。

新增 agent 策略较小时保留在现有策略表，以 `agent_policy` 版本化 JSON 保存细分权限，并继续用 policy_revision；字段扩展只面向 SQLite。旧 `management_agent_enabled=false` 总是能关闭恢复动作。命令权限与自动恢复权限分别明确，不能通过远程 package 命令绕过总开关。

### 11.2 索引和幂等规则

- 命令索引 `(device_id,uuid,status,created_at,command_id)` 和 `(status,expires_at)`。
- 管理创建请求使用唯一 idempotency_key；重复点击返回同一命令。
- 事件唯一 event_id，并验证同 ID 内容摘要相同；另加设备＋时间和 operation＋sequence 索引。
- 原 `(command_id,status)` 唯一索引保留服务旧更新事件。新事件不沿用它，避免同阶段多次尝试被吞掉。
- 命令投影通过明确状态转换表和序列推进，不套用旧 rank 模型。
- 所有外来状态时间与 server_received_at 分开；设备时钟不决定可信在线时间。

### 11.3 迁移和回退

- 新增表和可选字段，旧表语义不变，未知客户端 JSON 字段继续保留。
- 使用 legacy SQLite fixture 演练迁移、重复启动、数据卷重启和旧数据读取。
- 上线前做一致性备份并验证可恢复；不能用文件直接复制替代正在写入数据库的一致性快照。
- 老 API 镜像回退前关闭新命令创建；保留新表，不执行破坏性逆向迁移。
- 回退窗口内继续保留一个能接收新 agent 结果的兼容版本，或由 agent outbox 缓存，不能假设旧镜像理解新事件。
- 删除库存记录不等于卸载或撤销 agent。明确“删除展示记录”“撤销运维授权”“本机彻底卸载”三种动作。
- 撤销保留 tombstone/generation，防止旧设备通过自动首次绑定重新取得运维权限；未来重新授权必须显式进行。

### 11.4 容量设计

设备数为 N 时，30 秒命令轮询＋60 秒状态上报约为 N/20 次请求每秒，尚未包含策略刷新、旧 SSE 和主程序心跳。1,000 台约 50 次/秒；10,000 台约 500 次/秒。这是负载估算，不是性能承诺。

现有验签包含 nonce 写入、清理和 key last_seen 更新，应将这些写放入压测范围；WAL 不意味着 SQLite 支持多个并行写事务。

- 策略正常缓存 5 分钟，状态响应 revision 变化时提前刷新；不每轮重复拉取全部接口。
- 状态只更新最新投影，稳定内容不重复写大 JSON；上报仍刷新可信联络时间。
- 历史事件只记录状态变化和动作阶段；诊断包不存 SQLite BLOB。
- nonce、历史事件分批清理，有保留期与索引；不能每个请求无限扫描全历史。
- 先以 1,000 台为测试档位；达到目标规模再决定 broker 唤醒、批处理或存储演进，不预先引入消息队列。
- 新 SSE 若启用，由 Go broker 承载，有独立 agent 配额；PHP 不 sleep、不占用长轮询 worker。
- 当前 broker 快照读取全量策略及 pending 命令；扩展容量前评估查询范围，不直接将新队列也加进同一全量扫描。

## 12. 安装与 agent 自更新事务

### 12.1 服务和路径契约

保留服务名 `RustDesk`、`RustDeskManagementAgent`。保留 agent 当前受管根目录，新增受保护的 `transactions` 和 `recovery-runtime` 子目录；helper 不能位于将被替换或卸载的客户端目录内。

主客户端优先保留原安装位置、edition、架构和包类型。ProgramData 保底目录是降级运行路径，不默认覆盖正常安装登记。MSI 注册关系不允许仅修改服务路径就宣称完成安装修复。

服务契约包括可信可执行路径、正确引号、固定参数、账户、启动类型、服务类型及必要恢复配置。检查实际文件和重解析点，不采用字符串前缀判断可信路径。

### 12.2 单笔事务协议

```text
planned → package_verified → prepared → services_stopped → applying
        → validating → committed
                     ↘ rolling_back → rolled_back / rollback_failed
```

事务内容至少包含：transaction_id、触发来源、命令号、原包类型/版本、原服务配置、目标包摘要、可信路径引用、备份位置、阶段、helper 版本、结果和接续任务标识。秘密不进入参数列表。

1. 在受保护 staging 下载并校验候选包，不持安装锁等待网络。
2. 获取受 ACL 保护的全局安装互斥，重新核对意图、状态、包授权、磁盘空间、备份和 helper。
3. 保存原身份、配置和服务信息；所有可能改变系统的动作之前先持久化对应阶段。
4. 在受保护 recovery-runtime 部署经验证 helper，并注册当前事务的接续任务。
5. 验证接续任务配置正确且可执行；失败则不停止 agent。
6. 启动独立 helper，完成明确的接管握手，交接事务和互斥所有权。
7. helper 停止必要服务，等待实际退出，再执行安装或替换。
8. 启动主服务和 agent，验证版本、路径、身份与本地就绪。
9. 持久化结果后提交；随后清理临时任务、过期缓存和可删除备份。
10. API 不可达时进入结果补报，不重做安装、不回滚健康程序。

Windows mutex 的线程所有权不能跨进程直接“转让”。接管协议先持久化 transaction_id 和 handoff 阶段、确认 helper 已准备，再释放当前锁；所有竞争者取锁后先读活跃事务，只允许匹配 helper 接管，其他返回 busy。不存在把父进程 mutex handle 传给 helper 就自动转移所有权的假设。abandoned 仅证明持有者异常，取得者先恢复原事务。

本地持久化建议使用版本化 JSON 快照、原子替换和备份；关键边界执行 flush，并验证崩溃恢复。Windows 下采用适合替换语义的原生 API，不能认为“先移走原文件再 rename”天然无断电窗口。

### 12.3 接续任务

推荐使用固定二进制 helper 的临时 Windows 计划任务：SYSTEM、启动触发、失败后有界重试，任务参数只包含事务标识。任务定义、helper 和事务记录均受 ACL 保护。

- 仅在活跃事务存在期间保留；不是永久第二套自愈控制器。
- 启动前读取事务并重新核验目标、阶段和包摘要。
- 不联网获取新指令；仅继续当前事务或恢复旧可用状态。
- 与主动 helper 共用互斥，重复启动必须安全退出或接续。
- 可按 5 分钟重试，24 小时限制自动尝试；超过预算保留失败记录并告警，不无限执行安装。
- 若只是上报失败，任务不再执行安装；待恢复服务和终态可靠保存后可移除任务。
- 若 Task Scheduler 在设备上不可用或不允许注册，拒绝需要停止 agent 的自动更新；仍可保留不影响 agent 的服务恢复。

此机制提供重启接续，不保证硬件故障或全部恢复资产删除后的恢复。helper、计划任务和 MSI 的交互是必须实测的高风险项。

### 12.4 MSI 专项

- 不将 MSI 简化成目录复制；保留 Windows Installer 的产品和组件语义。
- 设计同版本 repair、升级、残留产品登记、源包不可用的不同执行方式。
- `0` 表示安装进程成功，`3010` 表示需重启完成，`1641` 表示已发起重启；都要继续核对事务实况。
- `1618` 视为安装忙碌，延迟重试，不立即判为文件损坏。
- 保持无自动重启策略；收到 reboot-required 时报告 `reboot_required`，由明确维护操作安排重启。
- MSI 回滚不保证所有外部自定义动作都恢复；必须检查主服务、agent、身份配置与实际版本。
- 永久组件不等于新二进制一定被安装，须验证文件版本资源、组件升级规则和 agent 实际运行版本。
- agent 的文件版本应随 agent 构建单调推进，不能仅在主程序 sysinfo 中宣称升级。
- MSI 修复指向保底安装目录时，核对原产品登记和正常安装目录关系，不能留下互相覆盖的产品状态。

### 12.5 EXE 专项

- 提取完整 payload 到 staging，验证文件集合和目标版本后再停止服务。
- agent 运行文件应先停止、确认退出，再做受保护替换；覆盖失败必须导致事务失败。
- 正常在线更新显式包含 ProgramData agent 的替换步骤，不仅复制 Program Files 内容。
- 备份服务配置、主程序目录及 agent 旧二进制；本地就绪前不删除备份。
- 失败恢复要覆盖“新服务已创建但启动失败”等中间态，先正确清理新服务再恢复旧契约。
- 不跨 MSI/EXE 自动转换，不跨 standard/SOS 自动转换。

### 12.6 agent.update 的首版实现

首版通过已批准的完整客户端安装包更新 agent，使用同一事务 helper。不要直接增加无签名的单 exe 下载接口。若完整包无法在不破坏现有安装的前提下可靠更新 agent，应暂时不开放 agent.update。

后续独立 agent 包必须有新的明确 target 契约、签名、文件集合、版本资源和旧版迁移测试。不能把 exe 安装包 target 冒充 agent 二进制 target。

新 agent 启动后先验证日志和事务 schema 能读取，完成本地自检并报告实际版本；如果不能启动，helper 恢复旧 agent。旧 agent 回滚必须能读取迁移前快照，不能使用已不可逆转换的状态。

SCM failure actions 用于 agent 意外崩溃后的重启，不替代安装主动停止后的恢复责任。初期只为 agent 配置有界恢复；主服务的失败恢复需单独核对主动停用和维护行为。

### 12.7 agent 自身的多层兜底

最终版增加“小型 RecoveryBootstrap＋Windows 常驻计划任务”，独立于主 agent 进程，只恢复 agent 和接续已有事务，不成为第二套主程序恢复控制器。

DTF 双服务正常停止是此入口的首要回归项，不能只测试 taskkill 模拟崩溃。启动器本身需与客户端/agent 一起进入安装包和批准恢复资产；首次/升级安装及彻底卸载都须管理任务生命周期。

| agent 故障 | 首选入口 | 后备入口 | 结果 |
| --- | --- | --- | --- |
| 进程崩溃 | SCM failure actions | 周期启动器 | 启动当前可信 agent |
| 服务意外正常停止 | 周期启动器 | 开机触发 | 运行意图允许时启动 |
| 服务删除/配置损坏 | 启动器固定服务契约 | 下一周期重试 | 重建/修正 agent 服务 |
| 二进制缺失/损坏 | 本地验证 agent 备份 | 已准备的签名 payload | 恢复批准版本，不下载未知程序 |
| Running 但核心循环挂起 | 启动器重复探测核心进度 | 有界重启 | 恢复检查循环，保留事务 |
| 升级/helper 中断 | 事务接续任务 | 启动器发现未完成事务 | 接续或回滚原事务 |
| Task Scheduler 不可用 | SCM 仍可处理崩溃 | agent 报告 degraded | 不宣称完整双入口 |

建议放在 `C:\ProgramData\RustDesk\RecoveryBootstrap\`，与主 agent 和客户端分别管理。任务 SYSTEM 运行、开机及每 5 分钟触发、单实例、有界时限，无需桌面登录。

上表有三行尚未实现，测试时按现状判：

- “二进制缺失/损坏”只做了缺失：`bootstrap.rs` `run_once` 只在 `symlink_metadata` 返回 `NotFound` 时进入 `restore_missing_agent`；文件存在但哈希不符直接返回 `agent integrity unavailable; no start attempted`，既不启动也不替换。后果是 agent exe 被截断或覆盖后，SCM failure action 反复拉起坏 exe，bootstrap 每 5 分钟只记一行，agent 永久离线、主程序侧 R1–R4 全部停摆，直到人工删掉坏文件或重装。另需 MSI、同 build、门禁打开三个前提。把“哈希不符”并入现有 restore 路径会改变“拒绝启动”这一安全失败语义，须维护者批准。
- “Running 但核心循环挂起”未实现：主循环是单线程 `recv_timeout(30s)`，没有进度戳、心跳或看门狗。后果同缺失恢复——进程不退出时 R1–R5、上报、命令领取全部停止，SCM 与 bootstrap 都只看到 `Running`。
- “Task Scheduler 不可用”只实现了 SCM fallback：`rescue.components.recovery_entry` 恒为 `not_assessed`，不产生 degraded。后台无法区分“双入口正常”与“只剩 SCM”。只读探测计划任务并上报 degraded 不改变恢复动作，但要新增上报状态与判定规则，须维护者批准。

这三行的共同点是都需要新状态或新生命周期规则，按 AGENTS.md「Corner cases raised in review」须维护者批准。

- 只读取固定受管记录和可信本地资产，无远程命令接口、任意脚本参数或整机自动重启。
- 本地彻底卸载和明确禁止 agent 运行优先；远程暂停客户端恢复不停止 agent。
- 活跃事务期间不抢占 helper，只调用已有可信事务接续入口。
- 核心进度来自检查循环，不以独立网络线程心跳代替；断网不判挂起。
- 挂起进程必须确认停止才能替换；无法停止时明确失败，不能启动第二个变更执行器。
- 与 helper 共用受保护生命周期互斥，避免升级与自恢复竞争。
- 默认不随每次客户端更新替换启动器；启动器升级另做事务，避免坏包同时破坏全部入口。
- 备份来自批准完整包并有可验证摘要/发布记录，不能按“文件存在”判可信。
- 启动器不兼容新事务/schema 时，阻断相关 agent 更新。
- 自动恢复建议最多 3 次/小时，之后冷却 1 小时重评估；持续崩溃时恢复批准旧 agent 或报告 degraded。

它覆盖进程、服务和局部文件故障；不能抵抗本机管理员/安全软件统一删除全部服务、目录和任务。同机多入口不等于异地带外管理。

## 13. 可信包、保底版本与本地安全

### 13.1 包验证链

1. 包解析精确匹配 product、edition、平台、架构、包类型和批准版本。
2. 验证 manifest schema、目标字段和发布签名；不只验证签名存在。
3. 流式下载到受保护临时文件，设置实际字节上限、空闲超时和总时限。
4. 比较大小和 SHA-256；执行前 helper 重新验证实际文件，防止校验后替换。
5. 解析 URL 并检查 HTTPS、精确 host、允许端口、无用户信息；重定向每跳重新校验。
6. 首版恢复包只接受既定下载域名下的批准路径。跨域镜像即使来自通用 manifest，也不自动取得 agent 执行资格。
7. 不因下载失败改用未签名包、debug 包或随意降低 TLS 验证。

Authenticode 若使用，应是与既有签名发布能力匹配的额外检查；不能将尚未具备的 Windows 商业证书当作首版必备假设。现有发布 manifest 签名仍是必须的可信来源。

### 13.2 保底版本

保底版本表示“最后一次验证可用的完整版本”，包含完整运行文件、包摘要、目标身份、配置兼容信息和最近成功验证记录。

- 保留当前可用版本及一份最后可用备份，缓存一份批准恢复包。
- 回退属于恢复本次事务原版本；不能任意执行网上旧版本。
- 新版本涉及不可逆配置迁移时，必须有配套兼容或快照恢复方案，否则禁止自动更新。
- 包撤销、最低安全版本和缓存过期规则明确；离线无法获知新撤销是客观限制，缓存不能被描述为实时授权。
- 已明确撤销的包不自动使用；离线无可用批准包时干净失败并保留诊断。
- 防病毒反复隔离时停止同包重装并报告；不自动关闭防护或添加排除。

### 13.3 网络与包来源 fallback

本地 R1–R4 优先，API 和公网不能成为救活主程序的必要前提。联网时：

1. API 正常，取得精确批准目标并核验签名。
2. API 不可达或认证异常，但已有有效批准目标和签名元数据，可从固定下载域名取得同一目标；新远程命令仍须认证。
3. 主 URL 失败，尝试签名元数据中本地策略允许的同域备用路径，目标大小与摘要一致。
4. 下载域名整体不可达，转本地包/保底客户端；无可用资产则保留 agent 等待恢复。

同域不同路径只能覆盖对象/路径故障，不能覆盖 DNS、证书或 OSS/CDN 整体故障。不为 fallback 私自改变 DOWNLOAD_BASE。真实跨域镜像需另行确认基础设施和允许域名，并完成签名与重定向验收。

当前实现与第 3 步不一致：自动 R5 只请求 manifest 的 `target.primary`，不读 `target.mirrors`，主 URL 失败后按 5/15/30/60 分钟退避重试同一地址；设备上存在 `rescue\current` bundle 时自动 R5 整体不运行。后果是 primary 持续 404 时恢复动作每小时重试一次、永远不会用到同域备用路径或镜像，直到 primary 恢复或运维下发远程命令。补齐自动路径的镜像回退可复用现成下载函数，但“有 bundle 时 R4 失败后进入 R5”需要新的阶梯跃迁规则，须维护者批准。

SSE 回退短轮询只能覆盖 broker/长连接故障，不能覆盖主 API 整体故障。本方案依靠本地自治覆盖控制面不可用。如果还要求主 API 宕机时后台继续远程操作，需要单独建设备用控制入口、数据一致性与命令防重，不能假装现有单入口已经具备。

### 13.4 本地安全和诊断

Windows 安装/升级可由用户明确同意配置两个精确 Defender EXE 排除项，首次默认关闭、升级沿用、静默显式参数、写后核验、失败不破坏安装。详见 [安装配置实现与验收边界](windows-defender-install.zh.md)。它不是 agent 自愈动作，不自动配置 360，也不扩大保底客户端/DLL/缓存范围；DTF 仍需独立启动器处理双服务停止。

SYSTEM 和管理员之外不能修改运行二进制、helper、事务、凭据、计划任务、缓存或本地禁止标记。目录隐藏属性只影响展示，不是权限控制。

检查祖先目录、重解析点、最终文件和可信路径；执行系统工具使用明确路径，参数数组或原生 API，不能依赖可劫持 PATH。helper 输入只引用受管事务，不接受任意恢复目录。

诊断包只包含固定日志和状态，排除密钥、密码、令牌、地址簿敏感数据及任意用户文件。建议单包 10 MiB、24 小时最多 3 次、后台保留 7 天；下载仍需管理权限。

## 14. 管理页面与操作权限

### 14.1 页面状态

设备列表至少分别展示：主程序心跳、agent 联络、恢复状态。详情增加本地服务、应用就绪、远控注册、当前版本/agent 版本、意图、最近事务和真实错误。

| 观测组合 | 展示建议 | 不可推导的结论 |
| --- | --- | --- |
| 主心跳离线、agent 在线、服务 stopped | agent 可达，主服务停止 | 不能直接认定主文件丢失 |
| 主心跳离线、agent 在线、本地 ready | 本地正常，主程序上报异常 | 不能保证远控可连接 |
| 主心跳在线、agent 无上报 | 主程序在线，agent 未确认 | 不能仅凭主版本判断 agent 正常 |
| 两者均离线 | 两条观测链均失联 | 无法区分关机、断网与两个进程故障 |
| 有未验证 401 请求 | 存在认证异常请求线索 | 不能将自报身份标为可信在线 |
| 已 installed，尚未 ready | 安装完成，验证中 | 不能显示恢复成功 |

agent 以 60 秒上报时，可初设 150 秒内 online、150–300 秒 stale、超过 300 秒 offline，且显示最后成功时间。主程序继续保持现有 20/90 秒规则。

### 14.2 能力和权限

主程序 build_seq 只用于展示“理论支持”，实际按钮依赖已授权 agent 的版本、能力和新鲜状态。旧版本显示“尚未确认 agent 能力”，不能允许无法执行的命令。

新增运维权限粒度：观察诊断、服务恢复、客户端安装、agent 更新、批量运维、身份重新绑定。可以在当前管理员会话基础上增加权限检查，不强行同时重构全站用户系统。

- 所有管理变更要求登录、CSRF、目标身份校验和操作审计。
- 重启、重装、启用主动停用客户端和批量操作明确展示影响并确认。
- 安装命令默认不打断活动会话；force 作为独立授权语义，不接受任意布尔值绕过全部前置条件。
- 参数在服务端和 agent 双重校验，不能仅靠按钮禁用。
- 首版发布包签名和服务端访问控制为基础；若要抵御 API 主机被攻陷后的合法命令滥用，需后续增加独立命令签发体系，不能声称当前设备签名已经解决。

### 14.3 批量操作

先选定冻结目标清单，生成 batch_id，限制并发、速率和失败阈值。建议首轮每批最多 100 台、同时安装最多 5 台，参数按试点测量调整。暂停只阻止未开始任务，不取消已进入替换阶段的事务。

每台设备结果独立，展示成功、失败、推迟、未支持和未知。批量接口不能用单个 HTTP 201 表示所有设备恢复成功。

## 15. 旧设备迁移与灰度发布

### 15.1 后台先行

1. 增量迁移 SQLite，发布新接口、能力开关和只读页面。
2. 验证旧 agent/policy、旧主程序 check/events、旧 broker 和管理页面兼容。
3. 默认关闭新的远程状态变更权限，新 agent 首次登记后仍先观测。
4. 在测试设备完成可信密钥与 agent 实例登记。

### 15.2 过渡客户端

构建包含新 agent、统一安装互斥、维护事务标记和本地健康 IPC 的完整包。旧主程序不需要先支持新协议，也必须能通过现有在线更新实际替换 agent。

EXE 更新缺失 agent 替换钩子是明确实施任务；MSI 则需证明永久组件和文件版本规则确实升级新二进制。四种旧包分别升级，不能只测全新安装。

迁移成功标准：ProgramData 的 agent 文件摘要正确、SCM 实际进程对应新二进制、新 agent 上报实际版本和能力、身份未变、主程序继续可用、重启后仍可管理。

### 15.3 已离线设备

| 设备情况 | 可行路径 |
| --- | --- |
| 主程序在线，旧 agent 在线 | 正常完整包升级后登记新 agent |
| 主程序在线，旧 agent 故障 | 完整包修复 agent 后验证 |
| 主程序离线，旧 agent 只能轮询，文件仍在 | 旧 agent 无服务启动能力；先用已有授权管理通道或现场启动/修复 |
| 主程序文件全失，旧 agent 认证正常 | 可评估既有缺失恢复能否装入新包；必须先用旧二进制验证 |
| agent 401 且主程序离线 | 先确定具体认证原因和生产版本；不能承诺仅改 API 即可恢复 |
| 两者均不可达 | 依赖其他带外授权通道或现场处理 |

不向旧 agent 下发它从未实现的命令。必要的路径兼容只能保留严格签名与身份校验，不能通过匿名命令、放宽公钥匹配或清空登记解锁。

### 15.4 一次在线升级的可行性结论

“一次在线升级获得新 agent 全部适用能力”可以作为目标，但不是当前代码已经具备的保证。当前实现存在三个明确障碍：

1. 旧 agent 只知道旧 policy 接口和缺失客户端恢复流程，不认识新增命令、能力协商或 agent 专用状态接口。
2. EXE 正常在线更新会替换主程序安装目录，但当前代码没有证明会更新 ProgramData 下运行的 agent。
3. MSI 包虽然包含永久 agent 组件，但必须确认 MajorUpgrade、相同版本升级允许项、组件文件版本规则和服务停止/重启结果确实更新正在运行的 agent。`Permanent=yes` 仅说明卸载保留，不等于替换成功。

首次桥接放在**下载目标包的新更新入口及其独立 helper**，旧 agent 无需理解新协议。现有主程序在 [updater.rs](../src/updater.rs) 的 2167–2169 行启动下载的 EXE 并传入 `--update`；[portable main.rs](../libs/portable/src/main.rs) 的 230–247、310–322 行解包后将参数传给包内新主程序，再进入 [core_main.rs](../src/core_main.rs) 的 `--update` 分支。因此新 EXE 的迁移代码能够在替换已安装文件之前执行，无需预先修改现场旧二进制。此处纠正之前“`--update` 必然由旧二进制执行”的判断。

MSI 路径则由现有主程序启动目标 MSI，迁移钩子须放进目标 MSI 可执行的安装链。两种路径都要在首次停服/覆盖之前部署受保护 helper、持久化事务和验证接续任务。仅在新主程序正常启动后补装 agent，无法覆盖主程序替换期间断电的窗口。

必须逐个检查现场使用的实际旧版本是否确实支持上述目标包调用。bridge 满足“旧调用参数兼容、完整目标包已验证、helper 脱离被替换进程/目录运行”才允许迁移。此前普通 EXE 目录复制没有 ProgramData agent 替换步骤，这仍是需要补齐的实现缺口。

该保证有清楚的适用前提：设备在线、旧主程序仍能运行且具有现有的有效更新授权/通路、目标发布兼容当前 edition/架构/包类型、磁盘和 Windows Installer 可用。若这些前提不成立，不能承诺在线升级成功。

### 15.5 首次迁移协议

一次更新请求对应一个稳定的 `migration_id`，在主程序和 agent 本地都能幂等重入。迁移事务阶段建议为：

```text
eligible → package_verified → migration_prepared → client_updated
         → new_agent_installed → new_agent_started → identity_bound
         → bootstrap_ready → capabilities_reported → complete
                                                   ↘ degraded / rollback
```

| 步骤 | 动作 | 完成判据 |
| --- | --- | --- |
| 1. 更新资格 | 更新前记录旧 client/agent 版本、edition、MSI/EXE、安装路径、服务配置和设备 ID/UUID | migration_id 与精确设备身份已本地持久化 |
| 2. 验证目标 | 校验完整签名 manifest、精确 target_key、包类型、摘要和安装参数 | 与服务端锁定目标完全匹配，不接受 `latest` 漂移 |
| 3. 准备迁移 | 下载目标包的新更新入口/独立 helper 检查 ACL、空间、任务；在停服前部署接续入口并备份身份、agent 和服务参数 | 新 agent 可安装且回退/接续资料已可读 |
| 4. 执行主更新 | 目标包新更新入口协调 EXE/MSI 安装事务；本次停服属于 `maintenance`，不写成用户主动停用 | 主包结果符合 MSI/EXE 语义；失败保留原服务和安装 |
| 5. 安装新 agent | 从同一已验证包的 agent 构建产物部署至 ProgramData；停止旧 agent 后确认退出，再替换并配置固定 SCM 服务 | 文件版本/摘要正确，SCM binpath、edition、package_kind、正常路径正确 |
| 6. 首启自检 | 新 agent 读取旧 state；迁移 schema 采用前滚可读格式；验证凭据但禁止静默生成新设备身份 | 新进程实际运行版本和 installation_id 与磁盘一致 |
| 7. 可信登记 | 用精确 ID＋UUID、公钥指纹及 enrollment_generation 绑定新安装实例；旧密钥仍匹配时原位迁移 | 后台返回明确绑定成功；未经授权不得启用高权限命令 |
| 8. 准备救援 | 安装/验证 RecoveryBootstrap、临时任务能力、保底客户端与签名离线包；保留旧 agent 至新 agent ready | `rescue_readiness` 对计划开启的能力为 ready |
| 9. 能力验收 | 新 agent 签名上报版本、能力集合、意图、策略 revision、SCM 和 rescue_readiness | 后台逐项确认需要的能力，不从主程序 build_seq 推断 |
| 10. 提交迁移 | 持久化 complete 并上报 migration event；确认主程序和 agent 均能继续通信 | 页面显示目标 client build、agent build、能力集合和迁移完成时间 |

迁移结束后允许新 agent 所有**本机已实现且服务端已登记、获授权、前置条件满足**的能力。设备上的主动停用、本地禁止标记、无活动的远控网络和 API 认证授权仍按原约束执行；“能力已安装”不表示每项动作可绕过这些限制。

### 15.6 中断恢复、旧版本回退与不能自动迁移的设备

- 每个阶段先持久化迁移意图；机器重启后由新部署的 bootstrap/helper 或新 agent 读取同一 migration_id 接续。旧 agent 不认识新事务格式，不能把它当作首次迁移接续入口。
- 主程序已更新而新 agent 未启动：由已安装的新 helper/bootstrap 继续部署 agent；无该入口则恢复旧 agent/服务，不能仅把主程序更新事件上报 `installed`。
- agent 已替换但登记失败：保留新本地 agent 的只读观测/本地自愈边界；高权限远程命令保持未授权，优先重试原绑定流程。
- 新 agent 不兼容旧 state 或不能启动：恢复旧 agent 二进制与旧 state 快照，再按旧协议运行；不能迁移后删除唯一旧副本。
- 主程序更新已提交而 agent 回退：客户端版本和 agent 版本分别显示；保留远程管理兼容门禁，重试 agent 修复而不是虚报整包回滚。
- MSI 返回 3010 时迁移状态为 `reboot_required`/`pending_reboot`，保留接续入口；不得在没有授权时强制重启。
- API 暂时不可达时本地安装和迁移日志继续持久化，登记/能力事件进入 outbox；不能重复安装来“补上报”。
- 旧 agent 401 但主程序在线：在现有主程序认证仍工作时，可以由主程序正常升级通路迁移，不放宽旧 agent 验签。
- 旧 agent 401 且主程序离线、agent 唯一恢复请求也无法认证：没有已授权请求通道就不能从远端下发新能力；需要现场或既有带外授权通道。不能通过匿名升级、清空密钥或开放通用命令绕过。
- 主程序离线但旧 agent 仍能正常认证和取得旧 manifest 时，只能执行旧 agent 已具备的恢复能力；“更新 agent”必须通过已实测的旧版恢复链，或先让主程序进入兼容升级入口。
- 两个组件都不可达，且没有本地可运行 bootstrap/离线安装包时，任何新协议都无法自动到达设备；此情形必须明确列为无法保证在线迁移。

### 15.7 四种安装包的迁移桥接

| 当前/目标 | 桥接策略 | 专项风险和验证 |
| --- | --- | --- |
| EXE → EXE | 旧主程序启动目标包 `--update`，包内新入口先部署独立 helper/接续任务，再替换主程序及 ProgramData agent | 实测旧包参数透传、权限、解包目录生命周期、agent 替换 |
| MSI → MSI | MajorUpgrade 安装与永久 agent 组件共同升级；使用独立 helper 避免 agent 自停止死锁 | 核对组件版本/文件版本、SameVersion、服务控制、1603/1618/3010 和既有 1921 回归 |
| EXE 首装/修复 | 安装程序部署启动器、agent 和服务契约，任何复制或注册失败必须返回失败 | 当前 after-install 命令中先 copy 再 stop 的次序必须重排并检查每个退出码 |
| MSI 首装/修复 | WiX 负责主产品组件语义；agent 事务状态供后续恢复核验 | 验证未登录状态、重装、repair、MajorUpgrade、失败恢复和卸载不复活 |

每种目标包必须从对应实际旧包开始升级，而不是以全新安装代替。升级包的构建流水线要确认客户端产物与 agent 产物来自同一 source commit/build identity；manifest 或迁移记录能绑定二者版本。不能混搭不同构建的客户端与 agent。

### 15.8 一次升级的强验收判据

一次在线更新只在以下条件全部满足时显示“迁移完成”：

1. 原 RustDesk ID、UUID、公钥指纹保持不变；没有静默新注册身份。
2. 新主程序版本、agent 文件版本、agent 运行进程版本、edition、package_kind 全部精确等于目标。
3. SCM 服务名、启动类型、账户、binpath/参数和服务状态符合契约。
4. 新 agent 能独立签名上报，后台接受最新 sequence 与安装代次。
5. 能力列表来自新 agent 实际响应，覆盖该版本发布声明的全部能力；旧命令仍按旧契约兼容。
6. 本地停用策略和服务端 revision 均未意外改变；运行意图未知时没有擅自启动主服务。
7. RecoveryBootstrap、恢复任务、保底客户端和离线包状态准确反映；计划开放的异地恢复能力已 ready。
8. 迁移事务达到 complete，outbox 结果可补报；重启后迁移状态仍完整。
9. 实际远控注册和一次真实远控会话验收通过；若目标网络不可用，只能把迁移显示为组件就绪、连接待验证，不能声称远控恢复成功。
10. 所有失败注入均能保留旧可用主程序或独立 agent 恢复入口；没有“主程序更新成功、agent 静默未更新”的假成功。

旧 agent 不支持新 capabilities 字段，所以“能力协商”必须是新 agent 安装后主动上报；服务端不等待旧 agent 声称支持新能力。migration event 应区分 `client_updated`、`agent_installed`、`agent_started`、`identity_bound`、`bootstrap_ready`、`capabilities_reported` 和 `complete`，每阶段幂等且可审计。

首次部署临时 helper/恢复任务必须提前到 `migration_prepared`，不能在 `bootstrap_ready` 才第一次补上恢复入口。后者表示常驻保底和全部资产验收完成。临时任务与常驻任务分开，不能清理迁移临时任务时删除长期 fallback。

### 15.9 灰度门禁

- 先在 win10-gs 真机验证（原隔离 VM 已停用、该机无快照，破坏性试验须先做完整备份并空跑恢复），再选少量可现场恢复设备。
- 第一批每个 edition/包类型至少一台，观测 24 小时。
- 再扩至约 5%，观测 48 小时；通过后扩至 25%，再全面开放。
- 首先开启观测，再开启 service.start/repair，再开启安装恢复，最后开放 agent.update 和批量操作。
- 多层 fallback、离线资产和常驻启动器全部验收后才标记异地“完整保护”；先期版本不能充当最终交付。
- 出现身份变化、agent 无法恢复、健康设备被反复重启或安装导致旧版本不可用，立即暂停后续扩量。
- 关闭新策略不会自动回滚已健康运行的新版本；需要回滚时按具体事务与兼容包执行。
- 发布和生产升级沿用两仓库既有流程，单独执行获授权的提交、tag、构建和部署动作。

## 16. 实施任务与最小回归面

### 16.1 必须先通过的可行性试验

按先后在 win10-gs 用实际包验证下面三个试验，再扩展后台命令和全量页面。任何试验失败，先解决具体包链缺口，不假定能靠协议补救。

| 试验 | 必须证明 | 不通过时 |
| --- | --- | --- |
| POC-EXE | 实际旧 EXE 调用新包 `--update`，新入口首次停服前部署 helper/接续任务，运行中的 ProgramData agent 可替换 | 暂停 EXE 全能力迁移承诺，保留原更新行为 |
| POC-MSI | 实际旧 MSI 升级永久 agent 组件，新旧版本规则及服务停止成功，无 Error 1921，自停止不死锁 | 修复 MSI 最小范围并重新跑旧包矩阵 |
| POC-RESUME | 停止 agent 后杀 helper、win10-gs 重启，任务恢复到明确终态且原身份不变 | 禁止开放自动安装与 agent.update |

试验代码和注入开关必须有测试构建边界；正式包不得暴露未授权故障注入入口。本方案估算以三个试验可通过为前提，不能用目前纯文档论证替代。

### 16.2 实施依赖

| 阶段 | 任务 | 主要落点 | 进入下一阶段条件 |
| --- | --- | --- | --- |
| A | 固化现状测试、生产故障证据格式、协议 fixtures | 两仓库 tests、本文契约 | 两端现有契约可重现 |
| B | 新状态与授权绑定、只读 API、能力上报 | API 新 agent 模块、SQLite migration、agent 状态模块 | 不改变主心跳与旧策略语义 |
| C | 本地健康 IPC、意图记录、服务状态机 | agent 专属模块、Windows 平台薄钩子、主程序 IPC | 停用、Pending、网络异常测试通过 |
| D | 统一互斥、事务日志、helper、接续、常驻启动器、离线资产 | agent install/transaction/bootstrap 模块、Windows 更新入口 | 四包故障注入和 agent 自身恢复通过 |
| E | 旧版兼容桥接、在线更新替换 agent、迁移状态机和回滚 | windows.rs 更新钩子、WiX agent 组件、migration 模块 | 四种实际旧包单次升级达成全部迁移判据 |
| F | 命令、claim、事件、outbox、管理操作 | API agent 模块、agent executor、页面 | 去重、断电、权限、SQLite/E2E 通过 |
| G | 包解析、保底缓存、多层 fallback 与 agent.update | agent package/install 模块、release 选择调用 | 离线/在线恢复链与包门禁通过 |
| H | 灰度、负载、告警和运维手册 | 两端配置、测试、文档 | 达到明确验收指标 |

表中阶段是工作包，不是严格线性排期：POC-EXE/MSI/RESUME 先行；B/C/D 是恢复底座；E 的桥接可先验证，但其“全部能力”最终验收依赖 F 命令/事件和 G 包解析/fallback 完成；H 依赖 E/F/G 的实际包矩阵。测试驱动、固定 fixtures、依赖恢复入口和证据格式在 A 开始建设，不能最后才补。

建议将新增 Rust 逻辑放在 agent 自己的模块树，SCM、健康、身份、执行器、事务、包校验分开。后台新增 agent 模块，不把几百行新业务继续堆入 index.php；index.php 只保留路由接入。模块拆分只针对新功能，不顺带重构旧更新实现。

必须改变的现有运行路径：

- Windows 正常在线更新：写维护事务、获取安装互斥、实际替换 agent；否则新旧两套恢复会竞争且迁移无法成立。
- Windows 安装/卸载服务：持久化正确意图，区分维护与主动停用。
- 主程序 Windows 服务业务进程：提供受保护的只读健康探测。
- MSI agent 组件：版本替换和 helper 协调；变更范围以实际验证结果为限。
- Windows 安装及彻底卸载：创建/验证启动器和任务，彻底卸载时移除，避免卸载后复活。
- API agent 路由、SQLite schema、设备详情投影、恢复控制页：提供独立 agent 事实。
- API 策略同步中 agent 专属字段的权威规则：避免 observed 覆盖 desired。

RustDesk 远控协议、固定配置、旧平台更新路径和旧更新命令解析无需为本功能重写。任何扩大到共享 trait、公共字段语义或跨平台重构的变化都须在开发评审中给出必要性证据。

## 17. 测试与可量化验收

完整执行顺序、TDD 规则、新机器 OpenCode 执行协议、全新安装/旧版本升级、四种 EXE/MSI 组合、后台 SQLite、Playwright、实际 Windows 故障注入和提交前全量门禁，统一以 [Management Agent 全量测试与新机器执行手册](agent-recovery-test-runbook.zh.md) 为准。本文保留架构级验收矩阵；实现时不能只执行本文的摘要表。

### 17.1 TDD 顺序

每个新行为先写并实际运行失败测试，再实现最小能力，再执行集成与真实包验收；“记录测试缺口”用于暴露尚未具备的验收资产，不能替代 TDD 红阶段。纯状态机用 Rust 单元测试；HTTP/SQLite 用本地 fixture；桌面与服务流程用实际 Windows 程序。业务分支覆盖率目标不低于 80%，空过滤器不算通过。

能力—行为—测试编号—证据路径必须闭环；环境缺少音频/双屏/远控第二端/测试机时是 BLOCKED，不是 NOT_APPLICABLE。代码开发机完成源码和候选构建测试，新机器执行实际包与故障 E2E，控制机保存外部证据。新机器仅安装产物时不重复要求拥有完整 Rust 编译链，但报告不能因此声称源码门禁已执行。

### 17.2 必测矩阵

| 类别 | 必测场景 | 必须断言 |
| --- | --- | --- |
| 服务 | stopped、absent、wrong binpath、disabled start type、Pending、marked for deletion、访问拒绝 | 正确状态分类、必要变更、无误重装 |
| 意图 | 主动停用、远程暂停、本地禁止、配置损坏、意图未知、维护停止 | 不越权拉起；原配置和意图保留 |
| 文件 | 主文件缺失、保底缺失、存在但损坏、依赖缺失、隔离、权限错误 | 可信安装选择或明确失败，旧可用数据保留 |
| 网络 | API 401/403/429/5xx、DNS/TLS 失败、ID 服务不可达 | 本地恢复独立，管理失败不引发重装 |
| 身份 | 未登记、旧公钥、变化密钥、UUID 变化、克隆、撤销重连 | 精确绑定、拒绝原因、无静默新身份 |
| 命令 | 重复 claim、同 ID 异内容、过期、unknown type/version/args、实例变化 | 持久化去重、正确拒绝、无重复副作用 |
| 事件 | 重复、乱序、终态后旧进度、多 attempt 同阶段 | 状态不倒退、历史完整、补报不重执行 |
| 包 | 错目标、同版本修复、禁止降级、大小/哈希/签名错误、重定向越界 | 拒绝执行、保留原版本和错误类型 |
| 安装 | MSI 1618/1603/3010、文件锁、磁盘不足、启动失败 | 分类正确、旧数据保留、agent 可用 |
| 中断 | claim 前后、停止服务前后、替换前后、验证前后、结果落盘/上报前后断电 | 按事务接续、不重复重启、不丢身份 |
| helper | 启动失败、接管失败、helper 崩溃、任务重复、Task Scheduler 不可用 | 未准备完成不停止 agent；失败可诊断 |
| bootstrap | 崩溃、意外停止、服务删除、文件损坏、核心挂起、与 helper 并发、彻底卸载 | 有界恢复、不绕过禁止、不双实例、不复活已卸载程序 |
| fallback | R1/R2 失败转 R3，R3 不可用转 R4，R4 不可用评估 R5，全失败到 R6 | 证据驱动、成功即停止、总预算有效、身份保留 |
| 在线迁移 | EXE/MSI 旧版本升级、迁移中断、agent 未替换、登记失败、回滚后重启 | 不报告假成功；主程序和 agent 版本/能力/身份分别核验 |
| 自更新 | 新 agent 不启动、schema 不兼容、替换失败、结果上报失败 | 恢复旧 agent 或保留明确恢复证据 |
| 并发 | 主程序更新＋自愈＋远程 install＋双 helper | 最多一个变更事务，其他推迟 |
| 后台 | CRUD、迁移、权限/CSRF、幂等、删除/撤销、旧 JSON | HTTP、真实 SQLite、页面结果一致 |
| UI | 桌面与 390px、加载/空/错、键盘、刷新、详情关闭 | 无溢出、不伪造状态、清理订阅 |

### 17.3 真实 Windows 验收

- standard EXE、standard MSI、SOS EXE、SOS MSI 全部覆盖；同机不叠加未清理安装。
- Windows 10 和 Windows 11 各至少一个可生成测试环境，服务模式和未登录桌面场景覆盖。
- 从实际在用旧版本升级，分别覆盖 standard/SOS、EXE/MSI，验证 ProgramData 实际 agent 文件和运行版本、能力集合、installation_id、服务参数、bootstrap/任务，再重启机器复核。
- 迁移前后分别记录主程序 build、agent build、包类型、edition、ID、UUID、公钥指纹和后台绑定代次；任一身份或组件不一致，迁移失败。
- 注入“主程序已替换但 agent 尚未替换”“agent 已替换但尚未登记”“bootstrap 已注册但新 agent 未启动”“MSI 3010/1618”“迁移中断后重启”，验证接续或回滚。
- 服务恢复后发起真实远控连接，验证画面、键鼠、必要提权及断开；不是只调用 IPC。
- 故障注入在 win10-gs 真机执行（原隔离 VM 已停用、该机无快照，须先做完整备份并空跑恢复），不在生产设备做断电或破坏性试验。
- 老主程序不支持健康 IPC、安装协调时验证降级模式，确认没有误判挂起或抢占安装。

### 17.4 建议验收指标

| 指标 | 初始目标 | 前提 |
| --- | --- | --- |
| 已安装服务意外停止恢复 | P95 ≤180 秒 | 意图明确允许、无维护/会话阻塞、不在启动宽限 |
| 开机后的服务恢复 | P95 ≤6 分钟 | OS、SCM 和本地文件可用 |
| 短轮询命令被接收 | P95 ≤45 秒 | 网络正常、无后台限流 |
| 可信 agent 失联展示 | 最迟 5 分钟 | 60 秒上报周期 |
| 本地可靠 outbox 补报 | 恢复联网后 P95 ≤120 秒 | 事件队列未触达限额 |
| 健康设备误重启/误重装 | 故障矩阵与试点中 0 次 | 不把有限样本宣称为永久零故障 |
| 注入安装失败后的可恢复性 | 每个规定注入点通过 | 原来有可用版本则保留/恢复；无旧版本则保持 agent 可管理 |
| 旧版本一次在线迁移 | 四种实际旧包全部通过第 15.8 节判据 | 新 agent 实际运行并上报全部适用能力；无静默旧 agent |
| 1,000 台等效负载 | 新 agent API P95 <500ms，错误率 <0.1% | 明确测试硬件、旧流量基线与磁盘配置 |

安装时长依包体、网络、磁盘和重启需求测量，不直接承诺统一 15 分钟成功。单次超时预算与动作结果分离，超时不能自动宣称已回滚。

### 17.5 仓库检查与证据留存

客户端实现完成后按 AGENTS 执行 cargo fmt、workspace tests、clippy、Flutter analyze/test；涉及 Flutter 时运行对应 widget/桌面集成验收。共享更新协议改动覆盖 EXE/MSI/AppImage manifest 选择，平台改动执行实际目标构建。

后台执行 SQLite HTTP 集成、直接 SQL 状态核对、页面 Playwright、容器构建、端口 80、自定义管理路径和卷持久化验证，以及 PHP/Python/Compose 和 diff 检查。MySQL 不扩展、不运行冻结门禁。

先源码/集成检查，再构建候选包，再真实包 E2E 和最终审查，完成后才能提交为完成或发布。不要要求依赖实际包的 E2E 在任何编译之前执行。同源码/参数/包摘要的证据可复用；修改后受影响证据失效。失败保留错误、事务、原数据与恢复结果，清理本轮临时资源，保留回归测试及必要外部证据。

### 17.6 异地恢复组合故障验收

以下必须使用真实构建的主程序、agent、helper 和 bootstrap 在 win10-gs 真机上运行。每项记录动作顺序、fallback 层级、服务/运行版本、设备身份、最终远控结果和后台投影。

| 注入场景 | 必须走通的路径 | 成功标准 |
| --- | --- | --- |
| 主程序退出，API 正常 | R1 | 本地自动恢复；真实远控连接成功 |
| 主程序退出，API 同时不可达 | R1/R2 | 本地仍自动救活；恢复联网后补报 |
| 主服务删除、主文件完整 | R2 | 重建标准服务，原身份不变 |
| 主文件损坏、公网断开 | R3 | 完整保底客户端启动，显示 degraded |
| 主/保底文件损坏、API/公网断开 | R4 | 批准离线包恢复，身份和配置保留 |
| 本地恢复包损坏、公网可达 | R5 | 下载正确目标并校验，拒绝损坏包 |
| agent 进程终止 | SCM → bootstrap | agent 恢复，随后能处理主程序故障 |
| agent 服务意外删除 | bootstrap | 无桌面登录条件下重建服务 |
| agent 文件损坏且主程序离线 | bootstrap 本地备份 → agent → R1–R4 | 两层救援完成，不生成新设备身份 |
| helper 停止 agent 后崩溃并重启 | 事务接续任务/bootstrap | 接续或回滚，agent 和可用主程序最终恢复 |
| 新客户端版本持续崩溃 | 事务回滚/最后可用版本 | 不循环装坏目标，旧版本仍可管理 |
| Running 但业务循环挂起 | R0/R1 或允许的无响应救援 | 有界完成，记录可能中断会话 |
| API 401、主程序远控实际正常 | 认证诊断，不进入重装阶梯 | 不重启健康客户端，不扩权 |
| 本地彻底卸载后重启 | 所有入口遵循卸载记录 | 服务/计划任务不复活客户端 |
| 所有恢复资产均不可用 | R6 | 显示明确不可恢复原因，不伪造在线或无限重试 |

建议启动器 agent 恢复 P95 ≤7 分钟（5 分钟任务周期＋启动验证）；这只适用于 OS/SCM/计划任务仍工作。缓存包且无需重启的离线客户端恢复建议试点 P95 ≤15 分钟，最终按四种安装包实测。断网期间只能验证本地 ready；网络恢复后才验证远控上线。

## 18. 风险、工作量与实施门槛

### 18.1 风险排序

| 风险 | 级别 | 缓解措施 | 发布阻断条件 |
| --- | --- | --- | --- |
| agent 自更新后失联 | 高 | helper、接续任务、旧版备份、启动自检 | 任一可复现中断点留下不可管理设备 |
| 主程序更新被自愈干扰 | 高 | 统一互斥、事务、旧版降级策略 | 并发产生双安装或反复切换 |
| 身份变化后管理错设备 | 高 | 精确绑定、实例代次、凭据保留 | 静默生成身份或模糊合并 |
| 首次绑定权限过宽 | 高 | 独立运维授权、受控登记、撤销 tombstone | 无可信登记仍能执行高权限命令 |
| 主动停用被覆盖 | 高 | 意图记录、本地优先、单独 client.enable | 普通恢复命令能绕过停用/本地禁止 |
| 故障目标反复重装 | 中高 | 目标熔断、动作预算、灰度暂停 | 健康设备或被隔离文件反复安装 |
| SQLite 写压力 | 中 | 短事务、索引、分批清理、负载验证 | 心跳和管理接口持续超时 |
| 诊断泄露配置 | 中 | 固定采集范围、脱敏、权限与保留期 | 私钥/密码进入日志或诊断 |

### 18.2 工作量估算

在熟悉两仓库、具备 win10-gs 真机和可用构建链的前提下，建议预留 25–45 个有效工程日完成开发、多层 fallback、启动器、首次迁移、故障注入与灰度准备；观察时间另计。这是范围估算，不是交付承诺。

| 工作包 | 估算 |
| --- | --- |
| 契约、认证登记、fixture 和迁移设计 | 3–5 日 |
| 状态采集、意图、本地服务恢复与 IPC | 4–6 日 |
| 安装事务、helper、接续、启动器和 agent 替换 | 9–15 日 |
| 后台命令、事件、页面和运维审计 | 4–7 日 |
| 四包旧版迁移、组合故障注入、容量与灰度准备 | 5–10 日 |

工作包有依赖，不能简单通过并行压缩安装事务与迁移验证。最容易低估的是 MSI 同版本修复、agent 文件版本替换规则、配置回滚和断电接续。

### 18.3 开发前与发布前的事实核对

开发前需要形成记录的事实：当前实际安装包版本、Windows 支持范围、四种包的 agent 版本资源、主服务账户与进程树、凭据实际路径、计划任务可用性、安装目录 ACL。

发布前必须补齐的生产事实：YXJ 401 的具体错误原因和两端部署版本、YJ 的 SCM 状态与启动路径、目标设备规模、磁盘可用量、现有授权远程管理通道。缺少现场证据不妨碍开发通用能力，但不能宣称已确认历史根因或能远程救回所有旧设备。

## 19. 评审结论与交付边界

该方案可以在现有系统上实施，推荐以增量模块、兼容接口和可验证事务推进。后台已有基础明显降低接口和控制台建设成本；Windows 安装生命周期、身份保留和旧 agent 迁移仍是核心工程量。

进入全面发布的必要条件：四种 Windows 包从实际旧版成功迁移并取得适用全部能力；主程序下线能自动逐级救活；离线包/保底客户端可用；SCM/启动器能兜底 agent；断电可接续；主动停用和本地禁止不被覆盖；两种心跳不混用；命令精确绑定、可去重可补报；真实远控冒烟通过。

本文只交付可行性与实施设计。未修改客户端/后台实现，未访问生产服务器，未运行安装包、HTTP 集成、负载或故障注入测试。计划指标和接口需在实现中验证，不能当作已完成的系统能力。
